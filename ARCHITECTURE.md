# Architecture

How the Pit's Burger code base is organised and the rules I follow in it. The code in this repository is an excerpt of a private client project (see the [README](README.md)), so some imports point at features that are not included.

## Stack

| Part | Technology |
| --- | --- |
| Backend | Node 22, Express 5, TypeScript 7 (strict, ESM), Zod 4 |
| Database | PostgreSQL 18, Drizzle ORM 0.45 (`pg` driver), drizzle-kit migrations |
| Frontends | React 19, Vite 8, TypeScript 7, React Router 7, TanStack Query 5, Zustand 5, CSS Modules |
| Tests | Vitest 5 and Supertest (backend), Vitest and Testing Library (frontends), Playwright (end to end) |
| Tooling | npm, oxlint (frontends) |

The repository holds separate npm projects (`backend/`, `ownerApp/`, `employeeApp/`, `e2e/`), no root `package.json`.

## Backend

### Layout

- `src/index.ts` starts the server; `src/app.ts` builds the Express app: middleware, route mounting, the error handler. Tests import `app`, never `index`.
- `src/<feature>/` is one folder per feature, for example `src/auth/` with `authRoutes.ts`, `authControllers.ts`, `authSchema.ts` (Zod) and a `helpers/` folder.
- `src/db/schema.ts` is the whole Drizzle schema in one file; `src/db/dbcon.ts` is the connection. Migrations are generated by drizzle-kit and never edited by hand.
- `src/lib/` holds shared utilities. `test/` holds the test database setup only; the tests themselves sit next to the code as `*.test.ts`.
- Feature routes are mounted under `/api`; only `/health` sits at the root. Relative imports carry the `.js` extension, as ESM requires.

### A request, step by step

1. **Validate.** The first thing a controller does is `schema.safeParse(req.body | req.query)`. The Zod schemas live in `<feature>Schema.ts` and also normalise input (trim, lower-case emails).
2. **Authorize and scope.** Middleware puts the signed-in user on `res.locals`; every query is scoped to that owner.
3. **Query.** Drizzle, with explicit column lists. A full user row is never returned; controllers select `publicUserColumns`. Multi-step writes run in `db.transaction`, and every query inside uses the transaction.
4. **Respond.** The payload is wrapped in a named key (`{ user }`, `{ position }`): 201 for creates, 204 with no body when there is nothing to return.

### Errors

- Every error response is `{ error: "English message" }` with the right status (400, 401, 409, ...).
- Validation failures are 400 with `{ error: "Invalid input", fields: z.flattenError(parsed.error).fieldErrors }`.
- Expected failures are returned from the controller. Anything unexpected is thrown, and the error handler in `app.ts` answers 500. There is no try/catch just to forward errors, because Express 5 handles rejected promises.
- A write that can race (two requests with the same unique value) is attempted and the unique violation caught, instead of "check, then insert".

### Data

- Business rules that must always hold are constraints in the database: unique indexes (also partial ones), composite foreign keys that include the owner, and so on. The API checks them too, so it can answer with a helpful 409.
- Tokens are stored only as hashes.
- Naming: files are camelCase and prefixed with the feature (`authRoutes.ts`). Controllers are named async function exports (`login`); the router is the file's default export. Tables are singular camelCase in code and snake_case in the database (`appUser` is `app_user`).

## Frontends

Both apps share the same structure.

### Layout

- `src/app/` has `App.tsx`, `providers.tsx` and `router.tsx`, where all routes are defined.
- `src/pages/` holds thin route components that compose features.
- `src/features/<feature>/` has `api/` (fetch functions and query hooks), `components/`, `hooks/`, `types.ts` and an `index.ts`, which is the feature's public surface.
- `src/components/ui/` and `src/components/layout/` hold shared components, one folder each with its `.module.css`.
- `src/lib/` has `apiClient.ts` and `queryClient.ts`; `src/styles/` has the design tokens (`variables.css`) and `globals.css`.

### Rules

- **Fetching.** All HTTP goes through `apiClient`; nothing calls `fetch` directly. In `features/<feature>/api/`, each endpoint is a plain function (`login.ts`) that unwraps the response, plus a separate TanStack Query hook (`useLogin.ts`). Components use the hooks only. Query keys are shared through `queryOptions` objects.
- **Errors.** Requests throw only `ApiError` (`status`, a user-safe `message`, `fields`). Components show `message` in an alert and `fields` under the matching inputs.
- **Validation.** Forms validate on the client in a `validation.ts` next to the form (plain functions, no form library) and merge in the server's field errors. The backend is the source of truth.
- **State.** Server data lives in TanStack Query only, including the signed-in user, which mutations update with `setQueryData`. Zustand is for client-only state, and server data is never copied into it. Local form and UI state is `useState`.
- **Imports.** Code outside a feature imports only from that feature's `index.ts`. API types are written by hand in the feature's `types.ts` and must match what the backend returns.
- **Naming.** Components are PascalCase in their own folder with a `.module.css` beside them and named exports only. Hooks are `useX.ts`; pages end in `Page`.

## Testing

- **Backend:** Supertest drives the real Express app against a separate PostgreSQL database (`<name>_test`), which is created and migrated automatically and wiped before every test.
- **Frontends:** Testing Library tests next to the components and hooks.
- **End to end:** Playwright runs production builds of the API and both apps against its own database (`<name>_e2e`), dropped and recreated every run, with one owner per test.

## Deployment

One Vercel project with three services (see `infra/vercel.json`): the Express API under `/api`, the employee app under `/employee/`, the owner app everywhere else. The database is Neon PostgreSQL. Contract PDFs go to Cloudflare R2.
